# PostgreSQLスキーマ・データ定義書

本書は、投資判断プラットフォームで使用するPostgreSQLデータの意味、型、粒度、制約を定義します。

本書は列の**意味・由来・運用ルール**を担当します。型やNULL可否などの構造情報はAlembicから生成される
`postgresql-schema-reference.md` が正本であり、本書の記載が食い違う場合は生成側を正とします。

スキーマ変更と文書生成の手順は開発ガイドを正本とします。CIは本書のテーブル・列とmigrationの
不足・余剰を検出します。

現在の定義は最新のAlembic revision適用後を対象とします。**スキーマ変更の履歴は
`backend/migrations/versions/`とgitが正本です。** 本書は履歴ではなく現在の意味を持ちます。

## 1. 共通データ規約

| 対象 | 規約 |
|---|---|
| 主キー | `BIGINT GENERATED BY DEFAULT AS IDENTITY`。代理キーは原則自動採番 |
| 日付 | `DATE` |
| 日時 | `TIMESTAMPTZ`、原則UTC。外部APIの日時を保持する場合は変換規則をETLに明記 |
| 時刻 | `TIME` |
| 真偽値 | `BOOLEAN` |
| 金額 | 財務実績は通貨の最小単位を`BIGINT`で保持。ユーザーが入力する予算・上限は小数通貨にも対応できる`NUMERIC(20, 2)` |
| 株価・比率 | `DOUBLE PRECISION`。通貨は `investment_target.currency`、単位は列定義または取得元定義に従う |
| 株式数 | `BIGINT`、単位は株 |
| 欠損 | 不明・未提供は `NULL`。空文字やゼロで補完しない |
| 列挙値 | `CHECK` 制約に列挙された小文字・大文字をそのまま使用 |
| 作成・更新日時 | `created_at` / `updated_at`。`updated_at`は更新処理側で設定 |
| 外部キー | PostgreSQL制約として常時適用する |
| 冪等性 | 自然キーに `UNIQUE` を設定し、取込処理はUPSERTまたは同等の再実行可能な処理にする |

## 汎用Trigger

現行の物理スキーマは、財務指標の数値比較を最初のTrigger定義として実装したものである。
`trigger_rule`から`trigger_response`までの履歴構造は共通基盤だが、条件定義は現時点で
`financial_metric_comparison`のみを受け付ける。同一Rule内の財務条件はALL / ANYで複数指定できるが、
ニュースイベント、公的統計、価格との異種条件結合は実装済みとは扱わない。実際の運用要件をPOCした後、Ruleの安定ID、version、
evaluation、responseを維持したまま、条件種別ごとの定義へ拡張する。

```text
trigger_rule（安定したRuleの同一性）
  └─ trigger_rule_version（条件の結合方法・発火時方針）
       ├─ trigger_rule_condition（1件以上の財務条件）
       ├─ trigger_rule_assignment（適用scope）
       └─ trigger_evaluation（Rule全体の判定結果）
            └─ trigger_response（人間・AI・システムによる方針の確認・上書き）
```

### `trigger_rule`

Ruleの同一性と現在の有効状態だけを持つ。具体的な条件は追記型versionへ分離する。

| 列 | 型 | 意味 |
|---|---|---|
| `rule_id` | BIGINT | Ruleの安定ID |
| `rule_key` | TEXT | 外部参照用のUUID |
| `is_active` | BOOLEAN | 評価対象として有効か |
| `created_at` | TIMESTAMPTZ | Rule作成日時 |

### `trigger_rule_version`

計算定義・条件の結合方法・発火時方針・採用理由をversion単位で固定する。
自由なSQL式は受け付けず、APIが公開する制約付き語彙から選択する。

| 列 | 型 | 意味 |
|---|---|---|
| `rule_version_id` | BIGINT | Rule version ID |
| `rule_id` | BIGINT | 安定したRule ID |
| `version` | INTEGER | 1始まりの改訂番号 |
| `definition_key` | TEXT | 計算定義群。現在はfinancial_metric_comparison |
| `logic_operator` | TEXT | all / any。配下Conditionの三値論理による結合方法 |
| `on_fire_decision` | TEXT | investigate / review_allocation / buy / sell / hold / no_action |
| `rationale` | TEXT | 採用・改訂理由 |
| `actor_type` | TEXT | human / agent / system / import |
| `actor_id` | TEXT | 設定主体の識別子。任意 |
| `created_at` | TIMESTAMPTZ | version登録日時 |

`(rule_id, version)`は一意。条件を変更するときは既存versionを書き換えず、同じ
`rule_id`に新しいversionを追加する。`trigger_rule.is_active`はRule全体の評価を停止するフラグであり、
versionの一部ではない。Rule versionには必ず1件以上のConditionを持たせる。この件数制約は
複数テーブルにまたがるためService層で保証する。

### `trigger_rule_condition`

Rule version内の個々の財務条件を順序付きで保持する。同じ指標を期初予想比と前年比のような
異なる比較軸で評価できる。条件を独立Ruleとして扱わないため、評価・作業キューはRule単位で1件になる。

| 列 | 型 | 意味 |
|---|---|---|
| `condition_id` | BIGINT | Condition ID |
| `rule_version_id` | BIGINT | 所属するRule version |
| `position` | INTEGER | UI・Evidence上の表示順。version内で一意 |
| `metric_key` | TEXT | revenue / operating_income / net_income |
| `comparison_type` | TEXT | forecast_variance / yoy / absolute / sign_transition |
| `operator` | TEXT | lt / lte / gt / gte / crosses_below / crosses_above |
| `threshold_value` | NUMERIC | 数値比較の閾値。符号転換時はNULL |

`threshold_value`の単位は`comparison_type`によって異なる。

- `forecast_variance`: `(actual - forecast) / forecast * 100`のパーセント値。例：`-10`は10%下振れ
- `yoy`: `(current - prior) / prior * 100`の前年同期比パーセント値
- `absolute`: 財務開示の当該指標値。通貨単位は取得・正規化定義に従う
- `sign_transition`: 閾値を保持せず、前回値と現在値の0越えを判

`sign_transition`は`crosses_below`または`crosses_above`のみ、かつ`threshold_value IS NULL`とする。
それ以外は`lt`、`lte`、`gt`、`gte`のいずれか、かつ閾値を必須とする。この整合性はAPIだけでなく
DBの`CHECK`制約でも保証する。

複数条件は三値論理で集約する。ALLは1件でも`not_fired`なら`not_fired`、それがなく
`unavailable`があれば`unavailable`。ANYは1件でも`fired`なら`fired`、それがなく
`unavailable`があれば`unavailable`とする。

### `trigger_rule_assignment`

Rule versionをどの集合へ適用するかを固定する。現在はすべてメンバー展開型であり、Mandate、Theme、
Watchlistを評価時点の構成Targetへ展開して、Targetごとに同じRuleを判定する。グループ全体を1件として
判定する集約評価は、配分乖離等の対応Factができるまで実装しない。

| 列 | 型 | 意味 |
|---|---|---|
| `assignment_id` | BIGINT | Assignment ID |
| `rule_version_id` | BIGINT | Rule version。現時点では1 versionにつき1 Assignment |
| `scope_type` | TEXT | investment_target / mandate / theme / watchlist |
| `target_id` | BIGINT | 個別Target scope。条件付き必須 |
| `mandate_id` | BIGINT | 投資枠scope。条件付き必須 |
| `theme_id` | BIGINT | Themescope。条件付き必須 |
| `watchlist_status` | TEXT | considering / monitoring / paused。NULLは登録銘柄すべて |
| `created_at` | TIMESTAMPTZ | Assignment登録日時 |

Target、Mandate、Themeは外部キーで参照し、`scope_type + scope_id`だけの無制約なポリモーフィック参照は
使わない。Theme membershipとMandate assignmentは評価基準日の有効期間で解決する。Watchlistは独立した
集合マスタを増やさず、`watchlist_entry`の現在状態から解決する。

### `trigger_evaluation`

入力snapshotはObserved全件の複製ではなく、判定に使用したEvidenceだけを保存する。
status=firedの評価がTrigger Instanceに対応する。物理テーブルの二重化は行わない。
同じ実績開示を再処理しても上書き・再通知しない。再生と実運用はmodeで明確に分離。

| 列 | 型 | 意味 |
|---|---|---|
| `evaluation_id` | BIGINT | 評価ID |
| `rule_version_id` | BIGINT | 判定に使用したRule version |
| `target_id` | BIGINT | scope展開後、実際に判定した投資対象 |
| `mode` | TEXT | replay / live |
| `event_key` | TEXT | 計算定義が作る冪等イベントキー |
| `as_of_date` | DATE | 評価基準日 |
| `status` | TEXT | fired / not_fired / unavailable |
| `reason` | TEXT | 比較可能または対象外・欠損理由 |
| `observed_value` | NUMERIC | 1条件RuleのDerived値。複数条件ではNULL |
| `reference_value` | NUMERIC | 1条件Ruleの参照値。複数条件ではNULL |
| `evidence` | JSONB | 条件ごとの入力値・判定・来歴・閾値・SQLハッシュ |
| `evidence_hash` | TEXT | 固定入力JSONのSHA-256 |
| `definition_version` | TEXT | 評価処理のバージョン |
| `orchestration_run_id` | TEXT | 定期評価を起動したAirflow Run ID。手動API評価はNULL |
| `on_fire_decision` | TEXT | 評価時点の発火時方針を固定したスナップショット |
| `evaluated_at` | TIMESTAMPTZ | 実際に処理した日時。過去へ戻さない |

`(rule_version_id, mode, event_key)`は一意であり、同じRule versionと入力イベントを再処理しても
判定履歴を重複生成しない。`as_of_date`は「いつの情報集合で判定したか」、
`evaluated_at`は「実際にいつ処理したか」を表し、意味を分離する。
`orchestration_run_id`は評価内容ではなく実行来歴であり、Evidence hashには含めない。

`unavailable`は「条件不成立」ではない。必要値の欠損、比較基準の不足、判定時点で未公表など、
判定不能だった状態を表す。`evidence`には判定に必要な入力と来歴のみを固定し、raw全体を複製しない。

### `trigger_response`

発火した評価に固定された方針を承認・上書き・保留した履歴と理由を追記する。
これは方針に対する判断であり、売買約定、調査実施、投資成果等の実行済みAction / Outcomeではない。
再生評価への記録は模擬対応として扱う。

| 列 | 型 | 意味 |
|---|---|---|
| `response_id` | BIGINT | 記録ID |
| `evaluation_id` | BIGINT | 発火した評価 |
| `disposition` | TEXT | accepted / overridden / deferred |
| `override_decision` | TEXT | 上書き後の方針。overridden時だけ必須 |
| `rationale` | TEXT | その対応方針を選んだ理由 |
| `next_review_on` | DATE | この発火案件の次回確認日。**deferred時は必須**（無いと作業キューへ戻らない）。Rule自体の定期監査日ではない |
| `actor_type` | TEXT | human / agent / system / import |
| `actor_id` | TEXT | 記録主体の識別子。任意 |
| `created_at` | TIMESTAMPTZ | 実際に記録した日時 |

Trigger Rule自体の有用性評価、誤発火、見逃し、Outcomeとの関係を扱うRule監査は現時点で
実装しない。運用履歴が蓄積し、評価基準が定まった後に`trigger_response`とは別の責務として設計する。
Ruleの停止は`trigger_rule.is_active`で扱う。BUY / SELL / HOLDは`on_fire_decision`として事前に定義できるが、
証券会社から取り込む実際の注文・約定Actionとは混ぜない。独立Decisionテーブルは設けず、Ruleの方針、
Trigger Instanceのスナップショット、Responseの承認・上書きによって当時の選択を再現する。MVPではすべての
発火時方針に人間の確認を必須とし、自動実行を導入するときに確認省略の設定を追加する。

Ruleの停止と完全削除は別操作とする。停止は履歴を保持したまま今後の評価対象から外し、再開可能とする。
完全削除は停止中Ruleに限り、配下のversion、condition、assignment、evaluation、responseも同一トランザクションで
削除する。誤登録・不要な試行を除去する管理操作であり、削除前に影響件数と復元不能であることを画面に表示する。


## 4. マスタ

### `capital_allocation_mandate`

投資目的・資金配分・成果測定単位の安定した同一性を保持します。UIでは「投資枠」と表示します。
予算・制約等の変更履歴は`mandate_version`へ追加します。

| 列 | 定義 |
| --- | --- |
| `mandate_id` | 主キー |
| `mandate_key` | DBの連番から`mandate-000001`形式で自動採番する不変キー。一意。ユーザー入力しない |
| `mandate_name` | 表示名 |
| `status` | `draft` / `active` / `suspended` / `retired` |
| `demo_expires_at` | 公開デモで作成した一時データの期限。通常・seedデータはNULL。期限後はAPIから隠し、cleanup jobが物理削除 |
| `created_at`, `updated_at` | 作成・更新日時 |

### `mandate_version`

判断時点の目的・予算・制約を再現するためのversionです。現在versionは`effective_until IS NULL`で、
Mandateごとに最大1件です。

| 列 | 定義 |
| --- | --- |
| `mandate_version_id` | 主キー |
| `mandate_id` | `capital_allocation_mandate`への参照 |
| `version_no` | Mandate内の連番。1以上でMandate内一意 |
| `purpose` | 投資目的・運用方針 |
| `allocation_weight` | 総投資予算に対するこの投資枠の配分率。0以上1以下。運用中・下書きの合計1以下をAPIで検証 |
| `budget_amount` | 0006以前のversionに保存された絶対予算の履歴。0007以降の新規versionではNULL。現行予算の計算には使わない |
| `currency` | 旧versionの絶対予算に対応する通貨の履歴。新規versionではNULL。現行予算の通貨は`capital_budget_version.currency` |
| `expected_return` | 期待収益率。例：5%は`0.05`。任意 |
| `max_drawdown` | 許容最大ドローダウン。`-1`以上`0`以下。例：-40%は`-0.4` |
| `horizon_months` | 想定投資期間（月）。任意 |
| `benchmark_target_id` | 任意のベンチマークInvestment Target |
| `review_cycle` | 見直し周期。`monthly` / `quarterly` / `semiannual` / `annual` / `ad_hoc` / `other`。任意 |
| `review_cycle_custom` | `review_cycle = other`のときの自由記述。それ以外はNULL |
| `next_review_at` | 次回見直し予定日 |
| `effective_from`, `effective_until` | versionの有効期間。現在versionは`effective_until IS NULL` |
| `change_reason` | 初版作成または改訂理由 |
| `created_at` | version作成日時 |

### `capital_budget_version`

投資枠へ配分する総投資予算の履歴です。現在versionは`effective_until IS NULL`で最大1件です。

| 列 | 定義 |
| --- | --- |
| `capital_budget_version_id` | 主キー |
| `version_no` | 総投資予算の連番version |
| `total_budget` | 投資枠へ配分する総額。0以上 |
| `currency` | ISO 4217の3文字通貨コード |
| `effective_from`, `effective_until` | versionの有効期間。現在versionは`effective_until IS NULL` |
| `change_reason` | 総投資予算を変更した理由 |
| `created_at` | version作成日時 |

### `mandate_target_assignment`

Mandate versionで採用する売買対象と目標配分範囲を有効期間付きで保持します。変更・解除時は既存行を
削除・上書きせず`effective_until`を閉じ、新しい状態は新しい行として追加します。現在の状態は
`effective_until IS NULL`で取得します。Theme membershipとは独立し、MandateとThemeを直接結びません。

| 列 | 定義 |
| --- | --- |
| `assignment_id` | 主キー。配分状態の各履歴行を識別 |
| `mandate_version_id` | 配分が属するMandate version |
| `target_id` | 採用するInvestment Target |
| `status` | `draft` / `active` / `suspended` / `retired` |
| `target_weight` | 任意の目標配分率。0以上1以下。有効Assignmentの合計1以下をAPIで検証 |
| `minimum_weight` | 任意の配分下限。目標配分以下 |
| `maximum_weight` | 任意の配分上限。目標配分以上 |
| `effective_from`, `effective_until` | Assignment状態の有効期間。変更・解除時に終了日時を記録 |
| `rationale` | このMandateでTargetを採用した理由 |
| `created_at`, `updated_at` | 履歴行の作成・更新日時。業務上の有効期間とは区別 |

同じMandate version・Investment Targetの履歴行は複数保持できますが、未終了行は1件までです。
Mandate自体を改訂すると旧versionの現行Assignmentを終了し、新versionへその時点の状態を複製します。
配分変更履歴を分析するときは、`mandate_version_id`、`target_id`、`effective_from`、`effective_until`を使います。

投資枠予算は`capital_budget_version.total_budget * mandate_version.allocation_weight`、Targetの目標金額は
さらに`target_weight`を乗じて取得時に計算し、保存しません。

過去時点の予算を再現する場合は、対象日時を含む`mandate_version`と`capital_budget_version`をそれぞれ
`effective_from <= 対象日時 < effective_until`（終了がNULLなら無期限）で選び、その時点の総額と配分率を掛けます。
0006以前の旧versionに配分率がない場合のみ、そのversionに保存された`budget_amount`と`currency`を
過去履歴の値として参照します。現行APIは現在値の表示用であり、この過去時点検索はまだ実装していません。

## 6. 関連テーブル

### `theme_investment_target`

テーマと銘柄の現在・過去の所属期間を保持します。現在所属している行は`effective_to IS NULL`です。
同じ組み合わせを外して再追加した場合は、過去行を上書きせず新しい行を追加します。

| 列 | 定義 |
| --- | --- |
| `membership_id` | 所属期間を識別する主キー |
| `theme_id`, `target_id` | テーマと銘柄 |
| `effective_from` | 所属開始日時 |
| `effective_to` | 所属終了日時。現在所属中なら `NULL` |
| `added_reason` | この分類・Universeへ追加した運用上の理由。任意 |
| `removed_reason` | この分類・Universeから除外した運用上の理由。任意 |
| `added_import_id` | CSV取込で追加された場合の`theme_membership_import.import_id`。手動追加は`NULL` |
| `removed_import_id` | CSV取込で終了した場合の`theme_membership_import.import_id`。手動解除は`NULL` |
| `created_at`, `updated_at` | 作成・更新日時 |

`effective_to`は`NULL`、または`effective_from`以後でなければなりません。同じ`theme_id`と
`target_id`について、`effective_to IS NULL`の現在行は部分一意インデックスにより最大1件です。
過去行は複数保持できます。

Relationship APIで追加すると、現在行がなければ新しいmembershipを作成します。すでに現在行が
ある場合は重複行を作りません。解除時は現在行の`effective_to`と`updated_at`を更新し、行自体は
削除しません。

`added_reason`と`removed_reason`は「CSV掲載」「分類誤り」などMembershipを変更した運用上の理由です。
投資対象として魅力的か、売買対象として採用するかというAssessment上の理由とは区別します。
`basket_weight`や投資判断上の採用理由はこのMasterへ保存しません。

### `theme_membership_import`

Theme構成CSVの取込単位と、時点付き差分の来歴を保持します。CSV原本はDB外に置き、参照先と
SHA-256を保存します。

| 列 | 定義 |
| --- | --- |
| `import_id` | 取込実行の主キー |
| `theme_id` | 対象Theme |
| `snapshot_at` | CSVが表す構成基準日時。Membershipの開始・終了時刻にも使用 |
| `import_mode` | `append`は追加のみ、`replace`はCSVを当該時点の全構成として差分同期 |
| `artifact_name`, `artifact_ref`, `artifact_hash` | CSV原本の名称、参照先、SHA-256 |
| `rationale` | 取込理由。任意 |
| `actor` | 取込主体 |
| `input_count` | CSVから解決できた対象数 |
| `added_count`, `removed_count`, `unchanged_count` | 差分件数 |
| `imported_at` | 実際の取込日時 |

同じ`theme_id × snapshot_at × import_mode × artifact_hash`は一度だけ取り込みます。`replace`は
CSVにない現在Membershipを終了するため、`--snapshot-at`の明示を必須とします。

## 9. 削除・履歴保持方針

- Themeを新しい分析・Trigger設定で使わない場合は`is_active = FALSE`としてアーカイブします。
  誤登録などで不要になった未参照Themeは、有効状態からでも物理削除できます。構成銘柄の所属履歴または
  Trigger設定から参照されるThemeは、来歴を保全するため物理削除できず、アーカイブして残します。
  アーカイブ済みThemeへ新しい構成銘柄は追加できません。投資対象の監視停止は
  `watchlist_entry.status = 'paused'`、Watchlistからの除外はその行の削除で表します。
- テーマと銘柄の所属解除は物理削除せず、現在行の`effective_to`を設定します。
- 時系列、取込履歴、財務開示は再現性確保のため履歴を保持します。
- Trigger Ruleは通常は停止して履歴を保持します。不要と確定した停止中Ruleは、関連するRule履歴・判定・対応を
  集約単位で完全削除できます。
- その他の外部キーには自動削除を設定していません。参照中の親レコード削除は失敗させます。
- rawデータ本体はDB外に保存し、`ingestion_run.raw_path` から追跡します。
